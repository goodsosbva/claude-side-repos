# 0001. 데이터베이스 선택: PostgreSQL vs MongoDB

## 상태
승인됨 (Accepted) — 2026-09-18

## Y-Statement

**상품/주문/결제** 도메인을 다루는 컨텍스트에서,
**주문 생성 시 재고 차감과 주문 항목(order_items) 간의 정합성을 원자적으로 보장해야 한다**는 문제에 직면하여,

우리는 **PostgreSQL**을 선택하고 **MongoDB**를 선택하지 않기로 결정했다.

이를 통해 **외래키 제약(FK)과 트랜잭션(ACID)으로 데이터 정합성을 DB 레벨에서 강제**하는 것을 달성하고자 하며,

**스키마 변경 시 마이그레이션 비용이 들고, 완전히 비정형인 데이터(상품 옵션 등)를 다룰 때 유연성이 떨어진다**는 점을 감수한다.

## 컨텍스트

- 도메인 모델이 `products` — `orders` — `order_items`처럼 명확한 관계형 구조이며, `order_items.order_id`/`product_id`가 FK로 참조 무결성을 가져야 함(`docker/init.sql` 기준)
- 주문 생성 시 "재고 차감 + 주문 생성 + 주문항목 생성"이 하나의 트랜잭션으로 묶여야 함(부분 실패 시 재고만 깎이고 주문이 안 생기는 등의 불일치 방지)
- 결제 연동(WBS T09~T10)에서 결제 상태와 주문 상태가 항상 일치해야 함
- 팀 규모가 2인으로 작아, 정합성 버그를 애플리케이션 코드로 일일이 방어하기보다 DB 제약에 위임하는 편이 운영 비용이 낮음
- 현재 스키마는 상품 스펙이 비교적 고정적(id/name/price/stock)이며, 상품마다 완전히 다른 임의 속성 구조가 필요하지는 않음

## 검토한 대안

| 옵션 | 장점 | 이 프로젝트에서의 단점 |
|---|---|---|
| **PostgreSQL** (선택) | FK/트랜잭션/CHECK 제약으로 정합성 보장, JOIN으로 주문 상세 조회 용이 | 스키마 변경 시 마이그레이션 필요 |
| MongoDB | 스키마 유연, 수평 확장 용이 | 주문↔재고 간 원자적 갱신을 애플리케이션에서 직접 구현해야 함(멀티 도큐먼트 트랜잭션이 가능하지만 관계형만큼 자연스럽지 않음), 참조 무결성 미보장 |

## 결과 (Consequences)

- 긍정적: 재고/주문 정합성 버그를 DB 제약이 1차로 막아줌, `order_items` FK로 고아 데이터 방지
- 긍정적: 관계형 조회(주문별 상품 목록 등)가 JOIN으로 단순
- 부정적: 상품에 카테고리별로 완전히 다른 속성(예: 의류 사이즈, 가전 스펙)이 늘어나면 `JSONB` 컬럼 또는 별도 정규화 테이블 설계가 추가로 필요
- 부정적: 스키마 변경마다 마이그레이션 스크립트 관리 필요 (현재는 `docker/init.sql` 수동 관리 — 향후 마이그레이션 도구 도입 검토 여지 있음)
- 후속 리스크: 단일 PostgreSQL 인스턴스는 SPOF이므로 별도 ADR/운영 대응 필요 (기존 리스크 분석의 #1, #2, #9 참고)
