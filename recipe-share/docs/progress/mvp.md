# MVP 구현

최종 갱신: 2026-09-20

## 무엇을 만들었는가

[feature-spec.md](../design/feature-spec.md) 의 P0·P1(F01~F10)을 화면까지 붙여 동작하는 형태로 만들었습니다. API 라우트 5개는 이미 스캐폴딩에 있었고, **없던 것은 화면 전부와 인증 상태를 다루는 두 엔드포인트**였습니다.

| ID  | 기능                | 화면                        | 비고                                  |
| --- | ------------------- | --------------------------- | ------------------------------------- |
| F01 | 회원가입            | `/signup`                   | 가입 즉시 로그인 상태가 됩니다        |
| F02 | 로그인              | `/login`                    | JWT httpOnly 쿠키                     |
| F03 | 레시피 작성         | `/recipes/new`              |                                       |
| F04 | 목록                | `/`                         |                                       |
| F05 | 상세                | `/recipes/[id]`             | 재료·조리순서를 줄 단위 목록으로 표시 |
| F06 | 사진 첨부           | 작성·수정 폼                | 저장 전에 `/api/upload` 로 먼저 올림  |
| F07 | 수정·삭제           | `/recipes/[id]/edit`, 상세  | 작성자에게만 버튼이 보입니다          |
| F08 | 내 레시피           | `/me`                       |                                       |
| F09 | 검색                | `/?q=`                      | 제목·재료 부분일치                    |
| F10 | 비로그인 차단       | 전 구간                     | 화면은 리다이렉트, API 는 401         |

새로 추가한 API 는 둘입니다. `GET /api/auth/me` 와 `POST /api/auth/logout` 입니다. 로그아웃에 서버 왕복이 필요한 이유는 토큰이 httpOnly 쿠키라서 JS 로 지울 수 없기 때문입니다.

## 설계에서 한 가지 갈라진 지점

[architecture.md](../design/architecture.md) 의 다이어그램은 화면이 항상 `fetch` 로 API 를 거치는 모양입니다. 실제 구현은 **읽기와 쓰기를 갈랐습니다.**

- **쓰기**(작성·수정·삭제·업로드·로그인)는 그림대로 클라이언트 컴포넌트가 API 를 호출합니다. F10 가드가 사는 자리가 거기이기 때문입니다.
- **읽기**(목록·상세·내 레시피)는 서버 컴포넌트가 질의를 직접 수행합니다. 서버가 자기 자신의 HTTP API 를 한 번 더 왕복하는 것은 절대 URL 이 필요하고 느리기만 합니다.

대신 질의가 두 벌로 갈라지는 것을 막기 위해 `src/lib/recipes.ts` 를 두고, **Route Handler 와 서버 컴포넌트가 같은 함수를 부릅니다.** 목록 검색 조건이 바뀌면 한 곳만 고치면 됩니다.

## docker compose 로 띄우기

```bash
docker compose up --build
```

`http://localhost:3000` 입니다. 이전과 달라진 것은 **`db-init` 서비스**입니다. 웹보다 먼저 한 번 돌아 `prisma db push` 로 스키마를 만들고 끝납니다. 이게 없으면 첫 실행에서 테이블이 없어 모든 페이지가 500 으로 죽습니다.

```yaml
depends_on:
  db-init:
    condition: service_completed_successfully
```

업로드 이미지도 named volume(`uploads`)으로 뺐습니다. 컨테이너를 다시 만들어도 사진이 사라지지 않습니다(risk-analysis.md #2).

## Playwright 로 검증하기

두 가지 방식이 있습니다.

**(1) 로컬 개발서버에 대고** — Playwright 가 서버를 직접 띄우고, 전용 DB(`e2e.db`)를 매번 비우고 시작합니다.

```bash
pnpm exec playwright install chromium   # 최초 1회
pnpm test:e2e
```

**(2) docker 로 띄운 것에 대고** — `E2E_BASE_URL` 을 주면 서버를 띄우지도, DB 를 건드리지도 않고 그 대상만 두드립니다.

```bash
docker compose up -d --build
E2E_BASE_URL=http://localhost:3000 pnpm test:e2e
```

검증 범위는 16건입니다.

| 파일                 | 덮는 것                                                        |
| -------------------- | -------------------------------------------------------------- |
| `smoke.spec.ts`      | 홈 200·콘솔 에러 0건, 없는 레시피 404                          |
| `auth.spec.ts`       | F01→F02 (가입·로그아웃·재로그인), 짧은 비밀번호 거절, F10 3종  |
| `recipes.spec.ts`    | F03·F06(사진 업로드 후 실제 200 확인), F04, F09, F08, 위장 파일 거절 |
| `ownership.spec.ts`  | F07 수정·삭제, 남의 글 수정 차단 (화면·API 양쪽)               |

## e2e 를 쓸 때 알아야 할 제약

**계정은 `auth.setup.ts` 가 한 번만 만듭니다.** 회원가입·로그인이 IP 당 분당 5회로 막혀 있어(risk-analysis.md #6), 테스트마다 가입하면 429 를 받고 엉뚱하게 실패합니다. 그래서 `owner`·`other` 두 계정을 setup 에서 만들어 `storageState` 파일로 저장하고 모든 테스트가 그것을 돌려씁니다. 화면으로 가입하는 경로 자체는 `auth.spec.ts` 가 따로 한 번 검증합니다.

같은 이유로 `workers: 1`, `fullyParallel: false` 입니다. 속도보다 재현성을 택했습니다. 인증을 건드리는 케이스를 추가하실 때는 분당 5회를 세면서 넣으십시오.

**업로드 테스트는 진짜 PNG 를 씁니다.** `storage.ts` 가 매직넘버를 검사하므로 가짜 바이트로는 통과하지 못합니다. 저장소에 바이너리를 넣지 않으려고 1x1 PNG 69바이트를 `fixtures.ts` 에 base64 로 박아 두었습니다.

## 검증한 것과 못 한 것

이 작업에서 실제로 돌려 확인한 것은 다음입니다.

- `next build` — 15개 라우트 전부 컴파일, 타입 검사 통과, 모두 동적 라우트로 잡힘
- `tsc --noEmit` — 오류 0
- `eslint .` — 오류 0
- `jest` — 7건 통과
- `playwright test --list` — 16건 인식

**돌려보지 못한 것은 e2e 실행 자체입니다.** 이 작업 환경의 프록시가 Prisma 엔진 배포처(`binaries.prisma.sh`)를 막아 DB 를 띄울 수 없었습니다. 즉 위 16건은 "문법과 구조가 맞다"까지만 확인된 상태이고, **실제 통과 여부는 폐하 환경에서 처음 확인됩니다.** 실패하면 그 출력이 다음 작업의 출발점입니다.
