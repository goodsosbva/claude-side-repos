# 리스크 분석 (설계 단계)

`architecture.md`, `feature-spec.md` 기준, 코드 작성 전 짚어야 할 리스크입니다.

| #   | 리스크                                             | 설계상 근거                                                                                                   | 영향                                                                         | 대응 방안                                                                                                                                                                    |
| --- | -------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | **배포 환경과 SQLite 파일 DB의 불일치**            | `dev.db`가 로컬 파일 하나. Next.js를 Vercel 같은 서버리스에 올리면 함수 인스턴스마다 파일시스템이 분리/휘발됨 | 배포하는 순간 쓰기가 유실되거나 인스턴스마다 다른 DB를 보는 정합성 붕괴      | 배포 대상을 처음부터 확정 — 영구 파일시스템이 있는 단일 서버/컨테이너로 갈지, Turso/libSQL·Postgres 같은 네트워크 DB로 초기부터 갈지 결정. "서버리스 + SQLite" 조합만은 피함 |
| 2   | **로컬 이미지 저장도 동일한 휘발성 문제**          | `public/uploads`에 런타임 저장                                                                                | 재배포/재시작 시 업로드 이미지 전부 소실, 서버리스면 애초에 쓰기 자체가 막힘 | 1번과 같은 배포 결정에 종속. 영구 디스크가 없다면 MVP라도 처음부터 S3(or 호환 오브젝트 스토리지)로 시작하는 게 나을 수 있음                                                  |
| 3   | **업로드 파일 검증 없음**                          | F06/architecture 어디에도 파일 타입·크기 제한 언급 없음                                                       | 임의 파일 업로드로 디스크 고갈, SVG 업로드 시 XSS, 확장자 위장 파일          | `saveImage()`에 MIME 화이트리스트(jpg/png/webp) + 용량 상한을 F06의 필수 요구사항으로 추가                                                                                   |
| 4   | **인가(authorization) 로직이 명세에 없음**         | F07 "내가 쓴 레시피 수정/삭제"는 있지만 "다른 사람 레시피는 수정 불가" 검증이 별도 명시 안 됨                 | IDOR — 로그인만 하면 아무 레시피나 수정/삭제 가능해질 위험                   | `/api/recipes/[id]` PUT/DELETE에서 `recipe.authorId === JWT의 userId` 체크를 F07 완료 기준(DoD)에 명시                                                                       |
| 5   | **SQLite 동시쓰기 한계**                           | Prisma+SQLite, 동시접속 규모 명시 없음                                                                        | 단일 writer라 동시 요청 많아지면 `database is locked`                        | MVP 규모면 문제 없음. 트래픽 늘면 1번 결정(Postgres 전환)과 함께 해결                                                                                                        |
| 6   | **인증 엔드포인트에 rate limit 없음**              | signup/login 명세에 시도 제한 언급 없음                                                                       | 무차별 대입 공격 노출                                                        | IP 기준 간단한 rate limit 추가 — 로그인은 보안 경계라 생략 금지                                                                                                              |
| 7   | **JWT 무효화 수단 없음**                           | 로그아웃/탈취 시 강제 무효화 로직 없음                                                                        | 토큰 탈취 시 만료 전까지 계속 사용 가능                                      | 만료시간을 짧게 설정하는 선에서 타협. 완전한 revocation은 P2 이후로 이동                                                                                                     |
| 8   | **"스키마 변경 없이 Postgres 전환 가능"은 낙관적** | architecture.md 확장 포인트 문구                                                                              | SQLite/Postgres 간 타입 차이로 실제 전환 시 손볼 곳 생김                     | 문서 문구를 "스키마 변경 최소화"로 정정, 전환 전 리허설 1회 권장                                                                                                             |

## 우선순위

1·2번(배포 환경과 DB/스토리지 불일치)이 나머지보다 먼저 결정돼야 하는 근본 리스크. 이게 정해져야 3~8번 대응 방식도 달라짐.
